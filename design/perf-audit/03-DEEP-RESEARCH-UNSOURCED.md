# Performance and Code-Quality Best Practices for Roblox (Alien Fusion)

Optimizing a complex mobile-first Roblox game (64 animated units, procedural skinned meshes, particles, etc.) requires careful attention to both **client rendering costs** and **script efficiency**. Below we summarize authoritative guidelines and findings (Roblox docs, engineer posts, Luau releases) on hotspots and best practices, flagging any “folklore” recommendations. We then provide a prioritized checklist of concrete optimizations (with numeric guidance where available).

## Client-Side Rendering Costs

**Skinned-mesh animation:** Applying transforms to many bones each frame is expensive. Roblox’s MicroProfiler tags animation work under tasks like `stepAnimation` (Humanoid/Animator). When moving/skinning MeshParts without a Humanoid, Roblox must rebuild spatial “FastClusters” each frame, causing large overhead. A proven trick is to include a dummy `Humanoid` in each animated model: this forces a single FastCluster per model and avoids per-frame rebuilds. In short, keep skeletons as simple as possible (fewer bones/influences per vertex) and prefer Humanoid/Animator-driven animation on the **client** whenever feasible. 

**Property writes (CFrame/Pivot, Attributes):** Setting `CFrame` or using `PivotTo` on many parts each frame (e.g. for IK or motion) can dominate CPU time. The MicroProfiler’s **Prepare/Perform** rendering steps will include these under geometry updates. Likewise, calling `SetAttribute` or repeatedly traversing with `GetDescendants` each frame adds script overhead. Best practice is to cache references and minimize per-frame hierarchy scans. (No direct Roblox benchmark is published, but community experience is that any nontrivial function call per part per frame scales poorly.)

**Instance creation/destruction:** Avoid creating or destroying many Instances each frame. Instantiation and cleanup incur GC and replication overhead. The Roblox performance guide explicitly recommends *object pooling*: e.g. recycle NPC models instead of respawning. This “reuse from a pool” reduces GC pressure and networking spikes.

**Particles, Beams, Effects:** ParticleEmitters, Beam, and lighting effects are **GPU-heavy** on mobile. The Roblox docs warn that changing ParticleEmitter properties “can have a dramatic impact on performance”. Overdraw from transparent parts (Neon material or transparency) multiplies fragment work. Use as few particles/lights as needed, batch effects, and throttle their emission rates. Turn off `CastShadow` on small or far-away parts, and disable unnecessary `PointLight`/`SpotLight` shadows – dynamic lights are very costly. In general, limit dynamic lights (suggestion: keep **<50** local lights, shadows mostly off on mobile) and use simpler materials (Plastic or SmoothPlastic) instead of full SurfaceAppearance where possible (PBR is heavier on older GPUs). 

**Draw calls:** Each distinct mesh/material triggers a GPU draw call. Roblox *instancing* batches identical meshes/textures into one call. Ensure identical asset IDs for repeated objects (don’t import duplicates). The docs emphasize keeping draw-call count low: try to reuse meshes and textures, use trim sheets or sprite sheets, and merge parts if possible. For mobile, aim for **at most a few hundred draw calls** visible at once. Larger meshes (more triangles) also slow rendering; use smaller **RenderFidelity** (set `MeshPart.RenderFidelity = Automatic` or `Performance`) to let Roblox swap in lower-poly LODs. 

**Culling and LOD:** Rely on Roblox’s built-in culling (frustum/occlusion) and use *Instance Streaming* for large worlds. For many NPCs, only spawn or enable them near players. Roblox now provides distance-based LOD: set `Model.LevelOfDetail = SLIM` (with StreamingEnabled) to show low-poly variants at range, and enable `Workspace.EnableSLIMAvatars` to auto-switch platform avatars to SLIM mode beyond a threshold. New “ClientAnimatorThrottling” (workspace setting) can also reduce update frequency of distant/small animators (default rollout in 2026). These strategies cut both CPU (fewer updates) and GPU load (fewer polys).

**MicroProfiler tags:** Use Studio’s MicroProfiler to identify spikes. Common tags to watch: **`RenderWait`/`Prepare`/`Perform`** (scene draw), **`StepAnimation`** (animation evaluation) and **`UpdateInvalidatedFastClusters`** (avatar/model updates), **`ProcessPackets`** (incoming network), and **`WorldLock`** (CFrame updates). The Profiler docs advise optimizing whichever tasks dominate frame time. For example, long “StepAnimation” bars mean too many active animators. Likewise, “RenderWait” or “Prepare/Perform” spikes indicate GPU bottlenecks (too many triangles, shadows, transparencies).

## Luau (Script) Performance

**Avoid per-frame allocations:** Luau’s garbage collector is incremental but heavy allocation in loops still hurts throughput. Official Luau guidance: *“avoid allocating memory in tight loops,”* e.g. don’t create new tables or strings each frame. Reuse tables via `table.clear`, use `table.create` to pre-allocate, and avoid throwing away closures/anonymous functions per update. Each allocation not only adds GC work but can cause micro-spikes. Likewise, caching global lookups in locals or using direct calls helps (Luau’s optimizer inlines many math/string functions, but for custom code you should use locals). Using `--!native` at the top of a module can trigger Luau’s native codegen, giving a modest (~1–2%) speedup in tight loops. Similarly, `--!strict` (type checking) won’t by itself make code faster, but improves maintainability and can catch logic errors early. 

**Math and Vectors:** Built-in operations on `Vector3`, `CFrame`, `Ray` etc. are implemented in optimized C code, so e.g. `Vector3.new`, `v1+v2`, `CFrame:ToWorldSpace` are fast relative to equivalent Lua math. However, each Vector3/CFrame is an object allocation: e.g. `(Vector3.new() + Vector3.new())` allocates temporaries. In hot loops (procedural animation), prefer to reuse a single CFrame or Vector3 variable rather than making new ones each frame. Fortunately, Luau’s optimizer will specialize many math calls; for example, Luau 5.41 improved builtin math calls to be very fast. But be mindful: e.g. `Vector3.new(x,y,z)` is slower than using a local and mutating it if possible. In practice, profiling is needed: track whether math operations appear under *Jobs/VM* in MicroProfiler.

**Parallel Luau (Actors, Tasks):** Luau’s Actors (`task.spawn` / `task.desynchronize`) can offload pure computation to worker threads. You could, for example, compute IK or enemy AI in parallel without blocking the main thread. But note **limitations**: Actors cannot yield or touch Roblox Instances (no Wait(), no touching parts, no GUI calls). They can do pure math, string/table processing, and return results. So you might spawn workers to calculate bone transforms or pathfinding logic, then apply results back on the main thread. In short: use parallelism **only for pure computation**, not for Roblox API calls. (This advice is generally cited by Roblox engineers, though not easy to quote directly.)

**Pooling vs. Debris:** For temporary effects (projectiles, vfx), it’s tempting to create parts and let `Debris:AddItem` clean them up. But pooling (reusing a pool of parts/objects) is usually faster because it avoids C++ allocations. The Roblox performance guide explicitly recommends pooling characters and NPCs. The same logic applies to bullet/projectile parts: deactivating and repositioning a pooled part is cheaper than destroying and rebirthing. Use `:ClearAllChildren()` or object caches when resetting complex models.

**RunService events:** On the **client**, use `PreRender` (the new replacement for `RenderStepped`) for camera/animation updates each frame. Use `Heartbeat` if you need a consistent 60Hz tick after physics, but note mobile may drop to 30Hz (32ms) if under load. In general, do per-frame visual updates in PreRender/RenderStepped, and do fixed-rate logic (like simulation with locked timestep) in Heartbeat/Stepped. The docs note that under heavy load, frames will be colored orange/blue depending on whether scripts or render took longer; aim to minimize both. (E.g. avoid `RenderStepped` loops that yield; prefer `BindToRenderStep` for better priority control.)

## Networking and Replication

**RemoteEvent payloads:** Whenever sending many unit states (positions, health, etc.) to clients, pack the data efficiently. Roblox supports binary packing: e.g. using `string.pack` to send multiple numbers in a short string. The Luau update notes even demonstrate packing a 3D state into ~16 bytes. Use `UnreliableRemoteEvent` for high-frequency updates (it uses UDP-like transport). Anecdotally, devs report an ~**900–1000 byte** soft limit on Unreliable payloads – above this the event may be dropped (so keep each message compact). For a swarm of units, send only what’s needed (e.g. position and maybe orientation quaternions, not full CFrames). Avoid tables of many parts per call; instead send arrays of simple numbers or packed bytes. 

**Rate and bandwidth:** There is no public hard cap given, but heavy remote usage (e.g. firing *every* frame for 64 units × 60 Hz × many bytes) will saturate both CPU and bandwidth. Roblox’s performance guide warns that “replicating data every frame that does not need to be replicated” is a common mistake. Instead, only send state deltas or events. For example, send unit positions ~20–30 times per second instead of 60 if interpolation is possible. Use interpolation on clients to smooth motion. Client should locally animate attacks/effects without waiting for server for every shot.

**Unreliable vs Reliable:** Use `FireAllClients`/`FireClient` on a **RemoteEvent** when data is infrequent or must arrive (e.g. match start). Use `UnreliableRemoteEvent` for streaming telemetry (positions, aim directions, etc.). Unreliable drops packets under congestion, but that’s acceptable for fast updates. The official doc notes UnreliableRemoteEvent is intended for “ephemeral” data. (If a message is dropped, the next one will correct the state.) 

**Best practices:** Chunk large messages; avoid sending tables of many Instances. Clean up Roblox-specific data (e.g. Animators, Humanoids) before replication. The guide suggests performing visual effects on the client entirely (send just an “explosion at X” event and let each client create particles). Also, tweening or physics on server replicates properties constantly – do these on client if smoothness matters. In short: **minimize per-player bandwidth** by sending compact, infrequent updates. Use profiling (Dev Console’s network stats) to watch average KB/s per client. If you see >100 KB/s, cut back.

## Level-of-Detail (LOD) and Culling

**Animation LOD:** Roblox now auto-throttles distant/small animations via the *ClientAnimatorThrottling* feature. By default (as of 2026) far-away NPCs may animate at only a few FPS. You should test how your game looks when this is on. Games with many NPCs often disable animation or use simpler loops for units far from the camera. In general, only animate and render details for units that are on-screen or near players.

**Geometry/Texture LOD:** As noted above, use `RenderFidelity=Performance/Automatic` and SLIM LOD for models/avatars. On a midrange phone, try to keep each character mesh at a few thousand triangles or less, and textures at 512×512. From Roblox docs: a 1024×1024 texture uses **4×** the GPU memory of a 512×512, so halving resolution is a huge win. Combine or atlas small textures to reduce count. Disable `CastShadow` on parts that are small or far away. Also, use the simplest collision fidelity (Box/Hull) for meshes that don’t need precise physics.

**Culling:** Frustum culling happens automatically. For extra control, manually disable or even destroy models that are far off (e.g. beyond view). Tools like **ChangeHistoryService** in studio can simulate distance streaming. Roblox’s instance streaming (with `Workspace.StreamingEnabled = true`) will unload entire models outside a radius.

## Code Quality and Structure

**Modular design:** Follow a consistent Luau style (see community guides like Aqua’s or Oxomo’s style guide). Keep code DRY and readable: use ModuleScripts to encapsulate AI behaviors, data, and utilities. Use enums or tables to store tunable parameters (data-driven design) rather than hard-coding numbers. Roblox encourages minimal use of global variables and prefers local/function scopes. 

**Error handling:** Use `--!strict` to catch type errors during development. It won’t boost speed, but it ensures correctness. Comments and clear naming are invaluable in complex systems.

**Avoid over-engineering:** A common sign of “too clever” code is heavy abstraction (many nested classes, metatables, or dependency injection) for a game script. Roblox games should be simple and performant: e.g. it is often faster to write clear loops than to use an overly generic functional framework. If a piece of code is hard to follow or debug, it might be over-designed. Focus first on concrete performance wins (see checklist) rather than perfect patterns. (For example, don’t prematurely optimize AI or graphics with GPU-like pipelines unless needed.)

**Style guide (Luau):** Roblox’s own scripting docs imply idiomatic Luau: use `local` variables, avoid needless metatables, prefer `for i=1,#list` loops or `ipairs` for tables. Always profile to confirm that cleaner code isn’t slower. (E.g. caching a frequently accessed part in a local can be faster than repeated `FindFirstChild` calls.) 

## Prioritized Optimization Checklist

1. **Reduce geometry and draw calls:** Merge identical meshes and reuse assets; enable instancing. Aim to keep visible triangle counts low (e.g. **<3000** tris per model, or use SLIM LOD for distant units). Use `RenderFidelity = Performance/Automatic` so Roblox can lower detail.  Combine textures (trim sheets) and prefer smaller textures (512px over 1024px uses ¼ the memory). Disable shadows and light sources on distant/small objects. *(Mathematically: a 1024×1024 texture = 4× the pixels of 512×512, so downsizing drastically cuts GPU load.)*

2. **Offload animations to client:** Play NPC and effects animations on clients, not the server. Do not use server-side Humanoids/Animations for many NPCs. (Client-authoritative animation lets you “skip” network replication of motion.) If using procedural bone updates, ensure only close units animate in full; throttle or skip updates for far units. Use Humanoids or Animators on models to batch skinned transforms and avoid FastCluster rebuilds.

3. **Cull and LOD:** Spawn/enable units only when near players. Leverage Roblox’s SLIM LOD: set `Model.LevelOfDetail = SLIM` and enable `Workspace.EnableSLIMAvatars` to automatically switch to low-poly models at range. Trust frustum/occlusion culling, but manually stream out distant parts if needed (use InstanceStreaming).

4. **Minimize dynamic objects:** Pool frequently created objects (bullets, effects, NPCs) instead of recreating them. Limit the number of active ParticleEmitters/Beams; reuse one emitter if possible. Set `Part.CanCollide/CanQuery/CanTouch = false` on purely visual parts to avoid unnecessary physics.

5. **Use efficient scripting:** In your animation/AI loops, do not allocate new tables/closures per frame. Pre-create arrays (e.g. `positions = table.create(64)`) and update numeric values in place. Cache service calls (`local RunService = game:GetService("RunService")`), and localize global functions (`local sin = math.sin`). For heavy math (IK, pathfinding), consider `task.spawn` or `task.desynchronize` to compute in parallel threads (no Roblox API calls there). Add `--!native` on compute-heavy modules to get Luau’s native compiler (gains ~1–2% speed).

6. **Optimize networking:** Use `UnreliableRemoteEvent` for position/aim updates. Pack data into binary strings via `string.pack` (e.g. 3 floats + 1 small int ≈16 bytes), rather than sending tables of Vector3. Keep each event payload ≤ ~900 bytes (to avoid drops). Send updates at ~20Hz per unit, not every frame. Rely on client interpolation. The goal is **<50 KB/s per player** ideally. Test with Dev Console’s Network Stats. Also chunk large data: e.g. don’t push all 64 positions in one huge event every frame – instead send smaller batches or only change deltas.

7. **Use profiling:** Regularly profile on a mobile device. The MicroProfiler guide recommends testing on a midrange tablet/phone, since desktops will not reveal issues. Focus on spikes (MicroProfiler timeline) and optimize the longest tasks (as tagged by frame color and task labels).

8. **Balance physics:** If using physics (Pathfinding or motors), disable or simplify joints for off-screen NPCs. Use adaptive physics stepping (`Workspace.PhysicsSteppingMethod = Adaptive`) so heavy scenes auto-throttle. Avoid having many unconstrained rigidbodies – anchor parts whenever possible.

9. **Follow Luau style/quality:** Write clear, maintainable code using ModuleScripts and data tables. Use `--!strict` to avoid bugs early. Avoid deeply nested metatables or over-abstraction unless necessary. (The official recommendation is pragmatic: optimize real bottlenecks first, not code style.)  

10. **Test and iterate:** After each change, re-profile. As Roblox docs note, even small changes (e.g. adding a Humanoid) can shift performance characteristics. Always verify that an optimization (like a pooled object or swapped LOD) actually improves frame time.
